# Akko Air 01 Linux configuration tool

## Intent and agreed scope

Build an open-source native Rust userspace configuration tool for the user's
Akko Air 01 on NixOS. Deliver a CLI first, then a TUI using the same backend.
The immediate outcome is a reliable left Fn / left Ctrl swap, understandable
profile selection, and recoverable settings without the Akko web app.
The user chose Rust and the order "cli then tui". The details below are the
builder's proposed defaults, pending approval. Publishing is a later step.

## Hardware evidence

The connected board identifies as device 3013 on wired USB `3151:5002`.
Its receiver was `3151:5006`. The model registry calls it
`yc3123_akko_air01_3m_1k`, but read-only hardware queries demonstrate Gen2
commands: `0x8A` returns a valid keymatrix, while `0x89` returns options.
Do not select a protocol from the chipset name or USB product ID alone.

There are four normal profiles. The captured active profile was 2. Profiles
0 and 3 already contain the desired swap; 1 and 2 have the defaults. Their
base keymaps differ only at slots 5 and 11. Thus profile selection can make
the swap appear lost; this is evidence for a cause, not proof that all
reported settings loss has that cause.

For this board, physical Fn is slot 5 and physical left Ctrl is slot 11.
The default Fn entry is `[10, 1, 0, 0]`. Left Ctrl is present in either
`[0, 224, 0, 0]` or `[0, 0, 224, 0]` form; preserve and correctly decode
both. Raw keymaps must round-trip without normalizing unknown entries.

A read-only backup already exists at:
`/home/ghadi/.local/share/akko-air01/backups/20261031-111435-before.json`.
It includes all four base profiles, the active profile's Windows/Mac Fn
tables, identification and selected settings. It is evidence and recovery
data, not a complete snapshot of macros, lighting patterns or all Fn tables.

## Approaches

1. Generic Linux remapper: good for ordinary key events, but cannot reliably
   move a firmware-only Fn key or configure onboard storage.
2. Extend monsgeek-akko-linux: contains useful transport work, but its
   chipset-based family detection selects the wrong command family here;
   its keymap presentation also requires Hall-effect switches.
3. A focused Rust CLI and later TUI: chosen by the user. Reuse documented
   protocol knowledge with attribution, keep the backend small, and validate
   against this physical board before claiming other-model support.

## First delivery: CLI

Working name and binary: `air01`. Project directory:
`/home/ghadi/perso/akko-air01-linux`.

Commands:

- `devices` and `info`: discover settings collections, identify the board,
  report USB connection, protocol evidence and active profile.
- `profiles` and `keymap`: inspect all four profiles and decoded/raw entries.
- `backup PATH`: export versioned JSON for all four base profiles and both
  Windows/Mac Fn tables for each profile; include identity and active profile.
- `restore PATH`: restore those tables and optionally the saved active
  profile. Validate the entire file and device identity before any write.
- `profile N`: select a normal profile and confirm the result.
- `remap SLOT ACTION --profile N`: edit a base-layer slot by explicit profile
  and numeric slot; support keys, Fn, disabled and lossless raw four-byte
  entries. Changes to Fn tables can use an explicit layer/OS option.
- `swap-fn-ctrl`: set the desired assignment idempotently, defaulting to the
  currently active profile. `--all-profiles` explicitly applies it to all four.
- Mutating commands print the planned changes; `--dry-run` does no writes.
  User invocation of a mutating command authorizes that operation; no repeated
  interactive confirmation is needed. Backups precede writes automatically.

The live validation will apply the requested swap to all four base profiles,
preserving the active profile and every other key. This makes the swap
consistent if the profile changes. Only mismatched slots are written.
Existing Fn-layer bindings, lighting, macros and other settings are untouched.

## Backend and correctness

Use a shared Rust library with discovery, protocol packets, transport,
typed profiles/slots/actions, snapshot files and verified operations. Prefer
`hidapi` with its pure Linux basic-udev backend to avoid system libudev link
issues on NixOS. The builder can choose crate versions and error/CLI libraries.
No asynchronous runtime is necessary for the first CLI.

Only wired USB writes in the first release. Receiver access is discovery or
read-only where verified; Bluetooth configuration is out of scope. An
unsupported model or ambiguous protocol remains read-only.

Enumerate the vendor settings HID collection, never grab typing interfaces.
Use bounded feature-report operations and reject short or malformed responses.
Use a per-device process lock, paced writes, a quiet settling period, and
read-back validation. Recheck identity and active profile before writing.
No firmware flashing, factory reset or Hall-effect commands.

Gen2 base read: `0x8A [profile, 0xFF, page, layer]`, eight 64-byte pages.
Fn read: `0x90 [os, profile, 0xFF, page]`.
Single base write: `0x0A [profile, slot, 0, 0, 1, layer]`, four data bytes at
8..12. Bit7 checksum is `0xFF - (sum(bytes[0..7]) & 0xFF)` at byte 7.
Fn writes must use their separately documented shape and receive the same
validation as base writes.

Assign a replacement Fn before overwriting the existing one. Reject a
transaction that would leave no Fn key unless the caller explicitly overrides
that safeguard. Restore must validate all entries before touching hardware,
skip unchanged slots, and report partial failure precisely. Do not blindly
retry writes, repeat flash commits, or claim rollback succeeded without
reading it back. Capture originals for every modified slot and attempt
verified restoration if the operation fails. If recovery cannot be confirmed,
stop and print the backup path and exact affected profiles/slots.

## Second delivery: TUI

Use the same backend, with profile selection, keymap inspection/editing,
backup/restore and explicit operation results. A simple Air 01 keyboard layout
can be added after validating physical-slot mapping; an accurately labelled
slot list is sufficient initially. No WebKit or browser dependency.

## Packaging and open source

Provide a reproducible Nix development/build setup, user-local installation,
a narrow udev rule for supported devices, README with examples and limitations,
and protocol notes distinguishing physical evidence from references. The
existing udev permission already enables this user's board; do not broaden
their system rules needlessly or change unrelated NixOS configuration.

Proposed license: GPL-3.0-or-later, with attribution and license notices for
any reused code. Primary references are `dniminenn/sharkfin` (especially
protocol/gen2.rs, derive.rs and docs/PROTOCOL.md) and
`echtzeit-solutions/monsgeek-akko-linux`. Keep this local until the user asks
to publish a repository. Do not include personal backups, local paths from
this design, logs or device captures in a public repository by default.

## Verification and limits

Test packet/checksum construction against the documented bytes, action
decoding including both Ctrl forms, malformed snapshots, unchanged-write
skipping, profile targeting, preservation of unknown slots, Fn ordering,
transport failures and read-back mismatch recovery with a fake transport.
Then verify real read-only snapshots, one requested remap with read-back,
and final consistency across all four base profiles. The user must perform
physical key presses and a power-cycle/reconnect to confirm behavior and
onboard persistence; report those as pending until actually checked.

The first delivery does not promise a background daemon, automatic repeated
restoration, RGB editing or macro editing. Add reconnect restoration only if
verified onboard storage still loses settings. Do not continuously rewrite
flash to mask a profile problem.
